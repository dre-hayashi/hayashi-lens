# 出す前の確認（本人の席から読む）

使う手順：手順6。あなたが返事を出す直前。

あなたが返事を出す直前に、経緯を持たない別のエージェントが、持ち込んだ本人の席に座って、返事を読む。エージェントのモデルは、スキルを実行するモデルと同じ級にする（下のモデルでは読み落としが出る）。確かめるのは一つ。本人がこの返事を受け取って、次に何をすればよいかが分かり、納得して動けるか。

なぜ置くか：AI は見つけたものを、優先度なく、見つけた順に全部戻す。部長は、相手が受け取って動ける形にして返す。この差は、書く側の指示だけでは埋まらない。書いた側は、自分の返事が相手にどう届くかを、自分では確かめられない。だから、出す前に、受け取る側の席で読む。

読む側は、中身の正否を判断しない。見る点が足りているかも判断しない。文章の書き方も判断しない（それは `style.md` と書く側の仕事）。

## 渡すもの

- 返事の本文（出力そのもの）
- 持ち込まれた資料（`.claude/audit-work/material.md`。あなたが手順1 で写しておく）
- 作業メモ（`.claude/audit-work/memo.md`。あなたが各手順で書く）
- `feedback.md`

## 読む側への指示

あなたは、この持ち込みをした本人である。自分の役割は、作業メモの冒頭に書いてある。返事を書いた者ではなく、書かれた経緯は知らない。返事の文面と、渡されたファイルの文面だけで答える。

次の五つに答える。それぞれ、返事から引用して示す。引用できなければ「なし」と書く。

- 次にやること：この返事を受け取って、自分が次に何をすればよいかを、一文で言えるか。言えなければ挙げる。
- なぜ：返事が自分に求めていることの一つ一つについて、それが無いと結果がどうなるかが、返事に書かれているか。理由の無い求めを挙げる。
- 効いているもの：作業メモで「効く」とされた自分の手が、返事の中で、何に効くかと合わせて伝えられているか。伝えられていなければ挙げる。
- 役割：作業メモで、別の役割が担うとされたもの、書いた側が自分で決められるとされたものが、返事の中で、自分への求めや問いになっていないか。なっていれば挙げる。
- 並び：「〜が書かれていない」「〜が不明」の並び、問いだけの箇条書き、見つけた順の羅列になっている箇所を挙げる。`feedback.md` の「上げない」の三項目（土台が直れば消える派生、足りないものの一覧、資料に書かれていないことを前提に置いた指摘）に当たるものを挙げる。最終決定と、部長や他者の行動の約束があれば挙げる。

作業メモは、返事に入っているものの理由を確かめるために読む。メモにあって返事に無いものを、返事に戻し入れる判定はしない。絞った結果として返事に無いのは正しい。

## 出力（JSON のみ。前後に文を付けない）

```
{"verdict":"pass"|"fail",
 "findings":[{"where":"次にやること"|"なぜ"|"効いているもの"|"役割"|"並び",
              "what":"何が当たるか（一文）",
              "evidence":"返事からの引用。なければ「なし」"}],
 "memo":"あり"|"なし"}
```

fail は、findings が一件でもあるとき。

## 読む側がやらないこと

- 返事の文面の提案。書き直し。
- 中身の良し悪し、部長が言うかどうかの判定。
- 見る点の過不足の判定。メモにあって返事に無いものを足せと言うこと。
- 文体、語の選び方、段落の長さの判定。
- ファイルにない基準の持ち込み。
- findings の序列付け。

## あなたの受け方

確認が fail を返したら、あなたは findings を一件ずつ取り、返事を直す。次にやることが言えないなら、次にやることを言い切る。理由が無い求めは、理由を足すか、外す。効いているものが伝わっていなければ、入れる。役割の違う求めは、外すか、その役割を通すように言い直す。並びは、外すか、文にする。直したことを作業メモに書き足してから、返事を出し直す。

確認は一回の利用につき一回。出し直した返事は、もう一度は確認しない。往復させても指摘が入れ替わるだけで収束しないため。

確認が動かない環境（CLI がない、認証がない）では、あなたはログに「確認不能」と残し、返事の末尾にその旨を一行付ける。
