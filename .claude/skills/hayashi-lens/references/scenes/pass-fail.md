# 完成したものの合否

確度：中（根拠：docs/casestudies.md）

「完成したので確認を」は、作業者が自分のタスクを終えたという作業終了の申告であって、完了ではない。完了は評価者の合意があって初めて成立する（`glossary.md`）。

本来は直属のリードやディレクターが応える。代理で見るときは、求められているのは代替承認であり、その席が見るべき点はすべて見る。プロダクトのコンセプト・目的・品質基準に照らして、全体がどう良くなるか、顧客にとってプラスかマイナスかを、監督者・品質責任者の目線で判断する。

## 土台
まず、受け入れ条件を満たしているか。合意した前提・制約、その役割が設計すべき場所が埋まっているか、評価できる材料（要因分析、仮説、対策の筋）が揃っているか。満たしていなければ不合格として返す。前提からずれているものは見るに値せず、個別の指摘を並べて直させない。

次に、施策の実施目的とターゲット。目的は与件ではなく評価の対象で、どの問題から立ち、今この製品で解くべきもので、達成したときどの価値が誰にとって良くなるかが言えなければ、目的が違う（`knowledge/game-design.md` 目的そのものが適切か）。目的が疑われるなら、設計の出来は見ない。設計そのものに善し悪しはなく、目的とターゲットに見合っているかで評価が決まる。同じ設計でも、目的が変われば評価は正反対になる。見合っているかは、意図した目的から顧客の行動まで、なぜそう動くかが一段ずつ繋がっているかで確かめる（`knowledge/game-design.md`）。

照らすべきコンセプト・目的・品質基準が資料にも依頼にもなければ、資料内の目的・前提から基準を立てて判断し、立てた基準を示す。

## 外側
評価する側は、仕様書の外にあるものを見る。その施策が影を落とす別の KPI、システム、要素。見る範囲は座った席の責任範囲で決まる。

## 代理の扱い
代理で見るなら、その席の責任範囲を狭めずに見る。上位者が承認・差し戻しをした後に、下位層へ再チェックさせる意味はない。持ち込みにその段取りが含まれていれば、意味がないと返す。
