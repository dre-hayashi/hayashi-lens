# 作業メモ
## 手順1
- 返す相手：ディレクター（部長宛ての相談を、出す前に持ってきたものとして読む）
- 求めていること：進めてよいかの承認（運用の決まりを変える提案）
- 届く先：社内。ただしリリース曜日はプレイヤーに直接届く
- 席：承認者（A）＋当初の運用から外れる提案（scenes/approval.md, plan-deviation.md）。媒体は Slack 壁打ち
## 手順2 土台
- 事実（本文）：来月から週次リリースを木→金に変えたい。理由は「週末に遊ぶ人に新しい内容をすぐ届けられる」。エンジニアリードと CS リードには未相談。
- 未確定：木曜リリースで何が届いていないのか（問題の事実・数字）＝本人が持つ事実。週末の障害・問い合わせ対応体制＝エンジニア・CS リードが出すもの（本人に出させず、通すよう言う）。
- 一問：木曜リリースのままで、週末に遊ぶ人に何が届いていないと見ているか、数字で見えている事実。
## 手順3
- 結果：プレイヤーに価値ある内容を届け続け、週次運営の品質（不具合時の対応含む）と信頼を保つ。
- 守るもの：リリース品質と不具合時の対応体制、スタッフの労働時間（週末対応）。
- 届くまで：問題の事実を立てる→エンジニア・CS リードと週末の障害／問い合わせ体制を確認→影響（イベント期間・告知）を整理→部長承認。
- 役割：問題の事実と提案の結論＝ディレクター。週末の障害対応・CS 体制＝各リード。承認＝部長。
## 手順4
- 効いているもの：プレイヤーの遊ぶ時間からリリース時期を考える見方は、目的（プレイヤー価値）に沿う。
- 説明：成り立っていない。木曜リリースでも内容は週末前に届いている。金曜移行で変わるのは、平日に遊ぶ人に一日遅れることと、不具合対応が週末にかかること。
- 経路：エンジニア・CS リードが飛ばされている。正当な理由（権利の履行）は示されていない→正当でない。両リードの確認を経てから持ってくる、と言い切る。
- 全体：今の理由では届きえない（理由が成り立たない）。問題の事実が立てば再判断。
## 手順5
- 返す：(1)理由が成り立たない（根）(2)両リードを通してから持ってくる（経路）(3)一問：何が届いていないか、数字の事実。
- 返さない／次の往復：イベント期間・告知の影響、hotfix 体制の詳細、腹案、週末対応の労務の詳細（リードを通す話に含まれる）。
- 面：承認者の席のまま、相談の口調。やらないこと＝承認の最終判断を言わない。
