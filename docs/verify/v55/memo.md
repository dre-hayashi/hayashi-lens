# 作業メモ
## 手順1
- 返す相手：QAリード（セクションリーダー層）。Slack スレッドの続きとして返す。モードは壁打ち。
- 求めているもの：助言・方針（「どうすればよいか」）。本人の結論は無い。
- 誰に届くか：社内。ただし削った範囲の品質はリリースで顧客に直接届く。
- 席：部長（品質の条件を定める側 D）。場面：consult、plan-deviation（QA期間という条件が、合意なしに実質的に動かされた）。

## 手順2 土台の事実（すべてスレッドから）
- 仕様書の締め遅れが続き、QA期間が毎回削られている（11/20 16:10）。
- 11月リリース：予定10営業日→6営業日（11/20 16:10）。
- 削られると分かった時点で、企画リードには毎回伝えた。返答は「次は気をつけます」（11/21 09:30）。
- ディレクターには言っていない（同）。
- リリース日は動かせないと思い、テスト範囲を自分で絞った（同）。動かせないかは確かめていない（「思っていた」）。
- 絞った内容はどこにも共有していない（同）。
- 11月リリースが既に出たかは不明。どちらでも「今日ディレクターに共有」の答えは変わらないので聞かない。

## 手順3
- 結果：リリースの品質を合意した水準で守ること。リリース判断が事実に基づいて行われること（会社・顧客からの信頼）。
- 守るもの：QA 10営業日の計画（品質の条件）。リリース日（確定日程と思われる。動かせるかはプロデューサーの判断で、本人は未確認）。
- 届くまで：
  1. 11月分：外した範囲とそのリスクを、今日ディレクターに出す。→ ディレクターが、未検証箇所の追加確認などを判断できるようにする。期限：今日。
  2. 次回以降：締め遅れが分かった時点で、ディレクターに「残り日数で見られる範囲／見られない範囲とリスク」を出し、仕様の優先順位（削る・次回へ回す）をディレクターが決める。
  3. 再発防止（締めが遅れる原因）：企画側の問題。「次は気をつけます」は人の注意頼み。ディレクター/PMが扱う。→ この件の手とは分ける。
- 役割：QAリード＝品質の最終判断、現場の状況をマネジメントに上げる結節点。ディレクター＝仕様の優先順位、品質の最終責任。PM＝スケジュール。プロデューサー＝リリース延期の判断。企画リード＝仕様の締め。

## 手順4
- 効いているもの：①削られるたびに企画リードに伝えている（検知した時点で声を上げている）。②10→6と数字で持ってきた。③優先度で範囲を絞ること自体は、短い期間での検証として成り立つ手。
- 成り立っていない説明：「リリース日は動かせないと思っていた」→確かめていない前提。仮に動かせなくても、何を削るかは品質の判断で、自分で決めて伏せる理由にならない。
- 逆に働く要素：絞った内容を共有していない → 周りは全部見た前提でリリースを判断する。削られても問題が表に出ないので、締め遅れが繰り返される。
- 全体の答え：今のやり方では品質は守れない（届きえない）。理由：品質を下げる判断が一人で、見えない所で行われ、決められる役割（ディレクター）に届いていない。
- 本人の役割の責任：果たされていない（セクションリーダーの品質責任、マネジメント層への結節点）。
- 経路：ディレクターが飛ばされた。理由「動かせないと思った」は正当でない。
- 別の役割：締め遅れの是正（企画リード/ディレクター/PM）、リリース日の判断（プロデューサー）は本人に求めない。
- まだ無いもの（本人の役割）：11月分の外した範囲の共有（今日）。次回以降、削られた時点でディレクターに範囲とリスクを出すこと。

## 手順5

- 返す：全体の答え／効いているもの（毎回声を上げた、数字、優先度で絞る手）／根／今日11月分をディレクターへ／次回以降は削られた時点でディレクターへ／締め遅れの再発防止は一言。
