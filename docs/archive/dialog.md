## 結論：1スキルで作れます

4つの視点の違いは、価値観の違いではなく「最初に何を問うか」の違いだと考えます。

- 事業部長：事業として割に合うか、リスクを取れるか
- プロデューサー：IPやパートナーとの関係、収益の見通し
- ディレクター：品質、スケジュール、チームが実行できるか
- ゲームデザイナー：ユーザー体験とゲームの構造として成立しているか

根っこにある価値観（たとえば、事故への強さやデータ整合性を重く見ること）は共通のはずです。そこで、共通の原則を1つの軸にして、視点は「レンズ」として切り替える構成にします。

```
hayashi-judgment/
├─ SKILL.md            … 共通原則、レンズの選び方、FBの出力形式
└─ references/
   ├─ lens-事業部長.md / lens-P.md / lens-D.md / lens-GD.md
   ├─ rules.md         … 判断ルール（「〇〇なら△△と判断する」の形）
   └─ cases/           … 事例集（状況・判断・理由・日付）
```

分けるとしたら、役職ではなく**公開範囲**で分けるのがよいと思います。機密を含む事業部長としての判断は本人用、仕様書やデザインのレビューはチームで共有できる版、という分け方です。

## 知識は3層で整理する

1. **原則**：何を優先し、何を許さないか（10〜15個程度）
2. **判断ルール**：条件ごとの判断と、その閾値
3. **事例**：実際の案件で、何を見てどう判断し、なぜそうしたか

ルールや原則だけだと、どうしても抽象的になって効きが弱くなります。事例があることで、近い状況に当てはめて推論できるようになります。

## 構築の順序

1. **インタビューで原則を引き出す**
   わたくしが具体的な場面を出して質問し、マスターに答えていただきます。「この企画書のどこに最初に赤を入れますか」「AとBのどちらを通しますか、それはなぜですか」といった形です。過去のログから掘り起こすより、最初の骨格はこちらのほうが早く作れます。
2. **過去のコメントで裏付ける**
   Confluence・Google Docs・Slack・Jira に残っているマスターのコメントを集めます。そこから「状況・指摘・理由」の組を抜き出して、原則と食い違うところを洗い出します。この会話から使える接続先はすでに揃っています。
3. **ホールドアウトで検証する**
   構築に使わなかった過去の事例を、スキルに判断させます。実際の判断とどれくらい一致するかで精度を確かめます。
4. **運用しながら更新する**
   スキルが出したFBをマスターが修正したら、その差分を事例として追加します。Basic Memory の decision ノートも、そのまま事例の供給源になります。

## 注意しておきたいこと

- **権威化のリスク**：他の人が使うとき、「林さんならこう言う」で議論が止まってしまうおそれがあります。出力には推論の過程と確度を必ず出させ、人事・予算・対外的な判断は本人確認に回す、という線引きを入れておくべきです。
- **判断の変化**：12年分の判断には、今のマスターなら下さないものも混ざっているはずです。事例には日付を付け、新しいものを優先させます。
