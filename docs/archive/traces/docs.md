# 判断トレース：コメント付き実在資料4件

形式：入力 → 最初に問うたこと → 辿った影響 → 比較と重み → 決定・要求 → 切り替え変数 → 問わなかったこと（通した箇所）

## T1. DH様とのMTG内容報告（QA委託先からの品質保証報告の要約、2026/09）

入力：委託先（DH）の報告書を現場が要約した資料。背景・現状・問題点・解決策・DHからの相談事項・新たな課題・今後のアクション。

最初に問うたこと（コメントの順ではなく、論理の順）
1. 用語の意味が一般と一致しているか。「Staging＝本番直前の最終確認環境」という一般定義と、現場の使い方（施策バグ検知環境）が食い違う → 用語の不一致そのものを事故の元として即刻是正。資料の中身より先に、言葉の土台を止めた。
2. 問題と解決が対応しているか。「メンテ中の新規ユーザー確認」は、問題点に新規ユーザー起因の記述がない → 問題→解決の筋が通っていない。
3. 解決策が具体か。「通しテスト」が何のテストか書かれていない → 我々が検知している問題を解決するものか判別不能。必要なことをやれている／いないの報告として不十分。
4. 事実の量。「十分に実施していない」＝一定はやっている → 何をどれだけやっているかをまず事実で出させ、照合する。
5. 責任の所在が片側に寄っていないか。DH側の問題もあるが現場側もやるべきことをやっていない → 現場側は何をいつから対策するのか。報告書にDH側の今後のアクションがない → 相手側の行動も書かせる。
6. 根本の備え。CDNを本番と共有→リーク懸念、という議論に対し「そもそもCDNにIPアドレス制限してないのか」 → 議論の前提になっている構成の基本的な欠落を疑う。

辿った影響
- 用語の食い違い → 以後のすべての合意と検証の前提が崩れる（事故の元）。
- 問題と対策の不一致 → 対策を実行しても検知していた問題が解決しない。
- 現場側の対策不在 → 委託先だけ直しても再発する。

比較と重み
- 細部（テストケースの内容）より先に、議論の土台（用語、問題の捉え方、構成の基本）を疑う。
- 相手（委託先）への指摘と、自分の側（現場）への要求を同じ重さで出す。片側に責任を寄せた報告は受け取らない。

決定・要求
- 用語の是正（即刻）。
- 現場側の対策・開始時期の明示。
- DH側の今後のアクションの明示。
- 「通しテスト」の定義と、現状実施量の事実報告。
- CDNのアクセス制限の有無の確認。
通すか差し戻すか：差し戻し（土台が崩れているため、内容の評価に入っていない）。

切り替え変数
- 問題と解決が1対1で対応していれば、解決策の内容評価に進んでいたはず。
- 「十分に」ではなく実施量が数字で書かれていれば、事実との照合に進んでいたはず。

問わなかったこと（通した箇所）
- 背景（QCの意識欠如などDH側の自己分析）には触れていない。相手の自己分析は争点にしない。
- 環境の構成（Test/Staging/Release/本番）の事実列挙自体には触れていない。
- 「今後のアクション：現場間で協議、進行担当者名」は、相手側の行動がない点以外は触れていない。

## T2. チュートリアルガシャ インシデント報告（版元向け報告書の草稿＋現場メモ、2026/08）

入力：版元（BNE）向けのインシデント報告書草稿。発覚経路・影響範囲・時系列・原因（直接／根本）・対策・総括。加えて現場の実態確認メモ。

最初に問うたこと
1. 原因の記述が「ヒューマンエラーリスクのある運用プロセス」で止まっている → ヒューマンエラー以前に、正常な開発体制とワークフローが定められていないだけではないか。「やるべきことを何もやっていない」と公言しているに等しい。
2. 工程が本来の目的を果たしていたか。メンテナンスとは「事前検証済みデータを本番へ移し、動作確認する時間」。メンテ当日にPRを取捨選択していること自体がおかしい。Stgで事前検証しているなら、当日はデータを移すだけの状態が普通。QA・開発はメンテ中に動作チェックして然るべきだが何をしていたのか。
3. 検査範囲外のリポジトリがあった点 → 「更新される対象の動作チェックは必須」。範囲の話ではなく、更新したものを確認しないことが問題。
4. 対策の前提が「感知できている」状態になっている → 認識の外にある対象をどう見つけるかが問題なのに、見つけられている前提のワークプロセス定義では承認できない。
5. 対策の具体性。「featureブランチを必ず作る現行ルールを継続」 → できていないのに継続？ルールがないからできていないのでは？ルールが運用されている証跡がなく説得力がない。「AIで機械的に判別」 → 何を見て判別するのか（プレフィックス無し、他ブランチ混入をどう見るのか）が書かれておらず、AIを使えば解決するという御花畑理論に見える。
6. 上流の文書。デザイナー側の仕様書はどうなっているか。キックオフで認識統一したなら仕様への書き戻しは？
7. 自動更新の担保。「自動だから安全なのではなく、自動だからこそ危険」。最新の差分が問題ない点を、誰がいつどう担保しているのか。

辿った影響
- 原因を個人のミスに置く → 体制とワークフローの欠落が残り、同じ種類の事故が別の場所で再発する。
- 「感知できている前提」の対策 → 認識外の漏れは次も検知されない。
- 対策に証跡・具体がない → 版元に出しても信用されない（版元向け報告書である点を重く見ている）。

比較と重み
- ライブ運営の品質検証とは「差分を正しく検知し、差分の動作を保証し、差分適用後も稼働し続けることを担保すること」。この定義に照らして工程を評価し、満たさないワークプロセスは稚拙と断じる。
- 「ヒューマンエラー」という説明は、仕組みの欠落の言い換えとして退ける。
- 対策費用やチームの負荷は一切論点にしていない。

決定・要求
- 工程ごとの実態の洗い出し（仕様書、デザイン仕様、実装の根拠、開発環境・Stg・本番メンテ前準備・メンテ時デプロイ＆検証の各結果）。
- 対策は「認識の外を見つける仕組み」として書き直し。
- ルールの存在と運用の証跡。AI活用は具体の判別方法まで。
- 自動更新差分の担保者・時期・方法の明示。
通すか：差し戻し。承認を得られる状態ではないと明言。

切り替え変数
- 原因が「仕組みの欠落」として書かれ、対策がその欠落を埋める仕組みで、証跡と具体があれば、内容の是非の評価に進む。
- 版元向け文書であること → 要求水準が上がる（信用に関わる）。

問わなかったこと
- 影響ユーザー数・件数・時系列の事実部分には触れていない。
- 止血対応（リソースリスト更新）には触れていない。
- 総括の文面（謝意・決意）には触れていない。文面より中身。

## T3. BNE対応方針（K-ID見積と、Ver.Zシナリオの予算差分プラン比較、2026/09）

入力：版元に伝える見積（工数・費用・専任時の期間と影響範囲）と、シナリオ制作の複数プランの観点別評価表と伝達方針。

最初に問うたこと
1. 見積のマージン。「マージン10〜15%を載せる。意見は工数が一番大きいエンジニアに聞く。不確定領域がほとんどなく実装に迷いがない見積なら10%、そうでなければ15%」 → 不確実性を計画に織り込む。幅の決め方と、誰に聞くかまで指定。
2. 計画内の辻褄。「専任化して対応するプランなので、QAも人が増えないはず」 → 前提（専任＝増員不要）と記述（QA増員必要）の矛盾を突く。

辿った影響
- マージン不足 → 版元に出した期間・費用が守れず信用を失う。
- 増員の矛盾 → 版元に出す費用の根拠が崩れる。

比較と重み
- 対外的に出す数字は、前提と記述の整合が取れてから出す。
- 不確実性の見立ては「実態を最も知る人（工数最大の担当）」から取る。

決定・要求：マージンの幅と根拠の確認、増員記述の訂正（現場が「増員必要」を取り消し）。
通すか：訂正を前提に通している（評価表の構造、プラン①の選択、伝達方針には触れていない）。

切り替え変数
- 不確定領域の有無でマージン幅を変える（10%／15%）。

問わなかったこと（重要）
- プラン比較の比重設定・評点の付け方・最高評点の分散は現場（藤沼）が自分で指摘しており、林は触れていない。現場が自分で直せているものは任せる。
- 伝達方針（プラン①打診、費用説明）、年度内完了に必要な着手時期の見解には触れていない。
- 費用の妥当性（単価、人月）には触れていない。

## T4. Ver.Z未協議領域 交渉戦略プラン（版元との費用負担交渉、内部資料、2026/07〜08）

入力：未協議費用（約3,300万円）の負担区分について、版元との段階的交渉プラン。戦略、ステップ①〜⑤、各段階の割合、最終ボーダー、責任所在の分析。作成者から「戦略・戦術が実現可能か」「ロジックの穴がないか」の確認依頼付き。

最初に問うたこと
1. 相手の出方への分岐。「代替案の逆提示があれば②へ」 → 逆提案の内容によって次が変わる。いくつかケースを見ておく必要がある。プランはあるか。
2. 数字の時間軸。「約33名縮小が必要」 → 期間に対する視点がない。33名は1ヶ月で解消する場合。年度内なら8ヶ月の猶予があり、削減は4〜5名のはず。

辿った影響
- 分岐がない → 交渉の場で相手の提案に対応できず、不利な条件で着地する。
- 期間を無視した人数 → 版元に対して事業影響を誇張した説明になり、数字の信用を失う。

比較と重み
- 交渉は相手の出方で分岐を用意する（自分が「ならどうするか」を先に決めておく）。
- 対外的に出す数字は検算する。桁が大きいほど、計算の前提（期間）を疑う。

決定・要求：分岐ケースの追加（現場が5ケース追加）、削減人数の訂正（4〜5名に訂正）。
通すか：訂正を前提に通している。

切り替え変数
- 相手の逆提案の種類（具体数字なし／割合提案／従来ルール提案／想定外）で次ステップが変わる。

問わなかったこと（重要）
- 段階の割合（10→20→25%）に数字根拠がないことは作成者自身が懸念として書いているが、林は触れていない。根拠が作れない数字は、交渉の構造（段階的に譲る、最終ボーダーがある）が正しければ許容している。
- 最終ボーダー（7:3）、絶対阻止ライン（45.5%）には触れていない。
- 責任所在の分析（文言解釈では分が悪い）には触れていない。
- 「DRE側で吸収するのは受け入れられない」という論調には触れていない。

## 4件に共通する辿り方（仮の復元）

順序
1. 言葉と前提が一般の意味・事実と一致しているか（T1用語、T3専任、T4期間）。ここで崩れていれば中身に入らない。
2. 問題の捉え方が正しいか。原因が個人・言い換えで止まっていないか、仕組みの欠落まで遡っているか（T2）。
3. 問題と対策が対応しているか。対策は具体か、認識の外を扱えているか、証跡があるか（T1, T2）。
4. 数字は前提（期間、人員、不確実性）込みで検算する（T3, T4）。
5. 相手の出方・不確実性への分岐が用意されているか（T3マージン、T4分岐）。
6. 責任の所在が片側に寄っていないか。自分の側の対策があるか（T1）。

重み
- 対外（版元・委託先）に出るものは要求水準が上がる。信用に関わる。
- 費用・負荷は論点にしない。
- 文面・謝意・自己分析には触れない。中身だけ。

通している（黙っている）もの
- 事実の列挙（影響数、時系列、環境構成）。
- 現場が自分で指摘・訂正できているもの（T3の比重、T4の分岐追加後）。
- 構造が正しければ、細部の数字根拠の弱さ（T4の割合）。
- 伝達方針・結論の選択そのもの（T3, T4）。土台と検算が通れば、選択は現場に任せている。

FBの形
- 問いの形が多い（「何のテストなの？」「プランはあるか？」）。断定は、土台が崩れているとき（用語、ヒューマンエラー論、御花畑理論）。
- 指摘には「普通はこう」という基準（メンテナンスの定義、Stagingの定義、featureブランチの常識）を添える。
- 修正案は出さない。何が欠けているかを示し、埋めるのは相手。
