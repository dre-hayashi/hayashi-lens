# 林の判断：重視するもの・判断軸・優先度の付け方（整理版）

根拠：コメント付き資料4件、会議15件の判断トレース（trace/docs.md, trace/m1.md）。各項目に根拠の場面を付す。
「確認要」と付けた項目は、材料から決めきれない点で、アンケートで問う。

## A. 守っているもの（衝突したときの優先順位。上が強い）

A1. 会社の法的・会計的な安全と信用。契約・法令（資金決済法、下請法、個人情報）・監査法人の指摘・上場会社としての体裁。
　根拠：09/01（契約に基づかない共有は原則禁止）、06/02（監査指摘は「文句は言うが守る」）、02/12（法務判断なしに条件を飲めない）、T2（版元向け報告は出せない）。
　→ これより上に置くものは見当たらない。「体制維持が必要」と言いながら監査指摘には従う（06/02）。

A2. スタッフの評価と体制（人を育て、残し、外部要因で評価を毀損させない）。
　根拠：06/18（1億の剥落を「プロダクト責任」と言うなら部長を降りる）、06/02（人を切る選択肢は最終手段）、09/11（後任を育てる、推進者を消さない）、10/17（人を切る話も「切る」と言うが、対象は「停滞を選ぶ人」）。
　→ 自分の地位はA2のために交換条件に出す（06/18、09/11）。
　確認要：A1とA2が衝突したとき（例：監査対応のために人を切るしかない）、A1を取るか。06/02ではA1を取った上でA2を最大限守る打ち手（契約切替）を探した。

A3. 今遊んでいる顧客の体験と信頼。
　根拠：10/17視座（優先度は現在＞未来＞過去無視）、10/17 OKR（運営タイトルで差別はやばい）、G4（資産を無価値にしない）。

A4. 事業数字。ただし「会社が継続できる損益分岐点＋10〜20%」まで。それ以上の収益最大化は目的にしない。
　根拠：10/17視座（金を稼ぎたいならゲームである必要はない）、11/19（損益分岐点を割る恐れがある時期は200万でも精査）。
　→ 数字は「守るライン」であって「最大化する対象」ではない。ラインを割る恐れが出たときだけ数字が最優先に跳ね上がる（切り替え変数）。

A5. 実績・運営ノウハウ・ブランド（ドリコムのゲームなら安定している、と言われること）。
　根拠：10/17視座。

A6. 現場の負荷・都合。これは上のどれに対しても理由にならない。
　根拠：06/02（現場の意見が上がっても絶対やる）、T2（対策費用は判断材料にしない）、O12。

確認要：A2とA3の順序。材料では両方「守る」と言うが、衝突場面がない。

## B. 資料・報告・相談を受けたときに確かめる順序（段取り）

B0. 入口：これは何のために、誰に向けて、誰が判断するために出されたものか。相手が取引先・版元なら水準を上げる。
　根拠：T1（DH側のアクションがない）、09/01（外向き資料と内部技術資料は別物）、08/11（相手にどう思ってほしいかの文章でなければならない）。

B1. 言葉と前提が一般の意味・事実と一致しているか。ずれていれば中身に入らない。
　根拠：T1（Stagingの定義）、08/11（開発環境とステージングは別物。「今の書き方だとお話にならない」）、T3（専任＝増員不要）、T4（33名は1ヶ月前提）、05/18（どの版の数字か）。
　→ 「第1ゲート」。08/11で本人が「これが僕の第1ゲート。明確にならない限り先に進めない」と呼んだのは「検証工程が機能していたか」だが、構造は同じ：土台が崩れていれば後ろは読まない。

B2. 問題の捉え方。原因が個人のミス・言い換え（ヒューマンエラー、作業が遅れた）で止まっていないか。仕組み・体制・工程の欠落まで遡っているか。工程は本来の目的を果たしていたか（メンテナンスとは何か、Stagingとは何か）。
　根拠：T2、08/11、C3。

B3. 問題と対策の対応。対策は問題に1対1で対応しているか。具体か（何を見て、どう判定するか）。認識の外にあるものを扱えているか。証跡はあるか。「AIで」「ルールを継続」は具体がなければ御花畑。
　根拠：T1（新規ユーザー確認は何の問題への解決か）、T2、08/11（AIを使っても解決できない。人がポカミスする前提）。

B4. 数字の検算。算出ロジックに辿れるか。前提（期間、人数、単価変動、不確実性のマージン、未消費分）が入っているか。他人の数字は自分で割り算する。
　根拠：05/18（1つずつ読み上げて検算、単価上昇が入っていない）、05/28（6億×1.5で9〜10億のはず）、T3（マージン10〜15%）、T4（期間の視点）、02/12（自分で図を描いて不足を発見）、10/10（計算式を自分で追う）。

B5. 責任者・期日・分岐。誰が判断し、いつまでに何をするか。相手の出方への分岐があるか。ダメだった時の手があるか。
　根拠：T4（逆提案のケース）、05/18（期限を自分の不在から逆算）、09/18（PMが「やってみる」で終わらせない）、O1。

B6. 責任の所在が片側に寄っていないか。相手（委託先・版元）への指摘と、自分の側（現場）への要求を同じ重さで。
　根拠：T1、08/11（委託先か開発側かの二択を絞ってから）。

B7. 以上が通ったら、選択や結論そのものは現場に任せる。
　根拠：T3（比重設定は現場が自分で直したので触れない）、T4（割合の根拠の弱さは構造が正しいので触れない）、09/18（必要なことは伝えた。あとは判断してくれればいい）。

確認要：B1〜B6の順序はこれでよいか。本人が明示したのは「第1ゲート」の存在だけで、順序は観察から復元した。

## C. 衝突したときの取り方（材料で観察できたもの）

C1. 体制維持 vs 短期の現場負荷 → 体制維持。負荷は理由にならない（06/02）。
C2. 会計ルール vs 体制維持 → 会計ルールに従い、その上で体制を守る打ち手を探す（06/02）。
C3. 相手への配慮・言い方 vs 伝達の正確さ → 正確さ。「嘘はつかない。観点を切り替える」（08/11、P5）。ただし版元には「会社から指摘が入っている」と言わせ現場を矢面に立たせない（09/01）。
C4. 収益最大化 vs 顧客 → 顧客。目標を無理に取り戻して振り回さない（10/17視座）。
C5. 今 vs 未来 vs 過去 → 今＞未来、過去は無視（10/17視座）。
C6. 現場の自律 vs 介入 → 一段下の管理層にだけ要求し、飛び越えない。「意図的に現場に入らない」（06/02）。ただし土台（用語、契約）が崩れていれば止める（09/01）。
C7. 個人の嗜好 vs 今遊んでいる人の受け入れ → 後者。「内心は思っているが何も言わない」（10/17視座）。
C8. 安全策で全部に付ける vs 意味の分かるプロセス → 後者（09/01 Confidential）。
C9. 一発で束ねて解決 vs 1件ずつ型を作って横展開 → 後者（09/18）。
C10. モアベター（作業が楽） vs リスク（回収できない膨らみ） → リスク（09/18）。
C11. 見込みを楽観 vs 保守 → 保守。「PLで見るときは最悪を見る」（06/18、05/18）。
C12. 自分がやる vs 相手にやらせる → 相手が分かっているなら任せ、聞き返されるのを嫌う。分かっていないなら自分がやって見せ、次回から覚えさせる（02/12、09/11）。
C13. 自分が下ろす vs 管理層から下ろさせる → 後者。「僕がやると業務命令になる」（09/11、06/02）。

確認要：C12で「任せると言った後に聞き返す」ことを嫌う一方、「迷ったら相談でいい」（09/01）とも言う。線はどこか。

## D. 判断を切り替える変数（これが変わると判断が変わる）

D1. 損益分岐点を割る恐れがあるか → 小さい増額でも精査（11/19）。余裕は「売上の日次変動で消えない幅」が必要（06/02の4000〜5000万）。
D2. 監査法人・法務・契約の指摘があるか → 「悲観しなくていい赤字」から「殺急に対策」へ（06/02）。
D3. 相手が社外（版元・取引先）か社内か → 社外向けは入口でブロック、水準を上げる。社内報告でも「きつい」水準はある（08/11）。
D4. 法律に関わる領域（個人情報、金、確率表示、監査）か → 仕様書・コードを渡す例外（09/01）。
D5. 不確定領域の有無 → マージン10%か15%（T3）。
D6. 自分の不在・会社の締め切り（月締め、予算編成、採用リードタイム）→ 期限を逆算（05/18）。
D7. 相手の役割（P／D／PM／リード／スタッフ）→ 求めるものが変わる。Pには価値と方向性、Dには文書の良し悪しとゲート、PMには障害除去と判断、スタッフには期待役割（09/18、09/01、09/11）。
D8. 相手が「分かっている」か → 任せる／自分がやって見せる（02/12）。
D9. 版元が追加依頼を出すか → 体制の維持／解散（06/02）。
D10. 相手の逆提案の種類 → 次の交渉ステップ（T4）。
D11. 今遊んでいる人が受け入れているか → 個人の嗜好を引っ込める（10/17視座）。
D12. 「ヒューマンエラー」か「仕組みの欠落」か → 後者として扱えるなら改善、前者で報告すれば問題になる（08/11、O18）。

## F. FBの出し方（人に対して）

F1. 問いの形が基本（「何のテストなの？」「プランはあるか？」「タクティカルアドバンテージは何？」）。断定は土台が崩れているとき（用語、ヒューマンエラー論、御花畑理論）。
F2. 指摘には「普通はこう」という基準（メンテナンスの定義、Stagingの定義、featureブランチの常識）を添える。
F3. 修正案は出さない。何が欠けているかを示し、埋めるのは相手。ただし相手が分かっていなければ自分がやって見せる。
F4. 個人を責めず仕組みを正す。「知らなかったことはできなくて当たり前。知った後どうするかが責任区」（09/01）。
F5. 「言語化できないなら分かっていない」。ふわっとした答えには「もっと出せるはず」と出させる（10/17視座）。
F6. 相手の感覚を世の中の水準と比較させる（「普段遊んでいるゲームでこの程度の問題が起きる？」08/11）。
F7. 自分の言い方の問題を自覚している（「多分俺の言い方がよろしくない。反省点が分かる」08/11）。

## G. レビューの目的（本人が08/11に言語化したもの。そのまま）

G1. 自分たちの立場を不用意に危うくしない。取引先に誠実であることは重要だが、それを優先した結果、自社のスタッフや開発体制に価値がないと思われることを避ける。
G2. 取引先と建設的な会話をするために、初歩的な、避けられて然るべき問題を入り口でブロックする。
G3. 今後も起きうる同じような問題について、内部スタッフが「あの程度の対応で良かった」「自分たちは間違っていなかった」という誤った認識を持たないようにする。本質は、書いているスタッフが本質を見逃している、考え方の軸がずれている、根本原因に気づけていないなど、対策を策定するための入り口に立てていないことへの懸念。
→ 1〜3を満たしてステークホルダーマネジメントを適切に行い、今日より明日、今週より来週と状態が改善していけるようコントロールする。優先順位：G1＞G2＞G3（AIの推察に「合ってる」）。3つは一つでも欠けると成立しない。

## H. 観点（立場）の扱い

H1. 「ディレクターとプロデューサーは本質的に一緒。評価基準としては見ている方向性が違うだけ」（09/11）。
H2. 自分の立場は「どのアイデアに金を出し、どれだけ事業的リターンがあるか」でしか判断してはいけない（B1の但し書き、10/17視座）。ゲームの中身・打ち出し方はプロデューサー・ディレクターに委ね、自分は土台側。
→ 観点は「同じ物差しで、見る範囲が違う」。資料の種類で観点を選ぶのではなく、資料の性質（対外か、法律か、数字か、人か）で確かめる項目が変わる。
確認要：マスターがかつて「立場で基準は変わらない」と言ったことと整合するか。
